# DX 5, part 2: the API between containers — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agents talk to each other and assign tasks: each team container reaches a narrow API on the host through its own Unix socket, with five verbs (`message`, `assign`, `release`, `ask-human`, `status`) checked against its capabilities, every call written to a journal.

**Architecture:** A long-running `forge api serve`, a systemd user service of the forge user (Ansible installs the unit), listens on one host socket per container. An Incus `proxy` device puts that socket inside the container; the API knows the caller by the socket a connection arrived on, never by the request. A request is one JSON line, validated by hand like the relay's; the verbs sit on part 1's host functions (`assign`, `release`, `sessionState`, `refreshTeamMirror`) and a new `deliverMessage`, which writes the text into a file of the target's container and types a one-line notice, written by forge alone, into its hc session: no agent text ever reaches a terminal. Agents call the API through `forge-team`, a small script forge pushes into each container.

**Tech Stack:** TypeScript on Node 24 (`node:net`, `node --test`), Incus proxy devices, herdr-core `hc` 0.1.20 in the containers, Ansible (`ansible.builtin.systemd_service` with `scope: user`).

**Spec:** `docs/superpowers/specs/2026-11-11-dx-5-herdr-core-design.md`, §5.2 (capabilities), §5.3 (assign and release), §5.4 (the API), §5.5 (mirror refresh on `message`), §5.11 part 2, §5.12, §6. Inputs from the part 1 acceptance run (PR #156, its "Pour la partie 2" section). Prerequisite: part 1 and PR #156 merged (they are, on `main`).

## Global Constraints

- Branch `agent/dx5-api`, from `origin/main`; one pull request, `Refs #92`. Title: `feat: l'API entre containers : sockets, verbes, journal, forge-team (DX 5, partie 2)`.
- Five verbs, no more: `message {to, text}`, `assign {to, task?, text}`, `release {to}`, `ask-human {text}`, `status {}`. Every request also carries `op`. Reply: one JSON line, `{"ok":true,…}` or `{"ok":false,"error":"<reason>"}`, then the connection closes.
- Caps, a memory guard against a runaway client, not a rule on content: a request line at most `REQUEST_MAX = 2097152` bytes (JSON escaping can grow a text sixfold); `message` and `ask-human` text at most `TEXT_MAX = 262144` bytes in UTF-8; an `assign` instruction at most `INSTRUCTION_MAX = 65536` bytes (the value of `MAX_INSTRUCTION` in `cli/lib/commands/team.ts:30`, which then imports it). Over a cap, the refusal says to put the content in a file of the branch and send its path.
- Text rules (every text an agent sends): not empty after trim; no exact occurrence of a secret forge handed out (the host's Claude token, `requireClaudeToken()`; the `tickets` secret joins in part 3). A refusal names its rule, never echoes the secret. Any other content is accepted, control characters included: the subject of a discussion may be exactly those. Whatever prints agent text on a person's terminal escapes it with `printable`/`printableText` (`cli/lib/printable.ts`; part 3's `team watch` and `answer`).
- Identity: the host socket. Request fields never name the caller.
- Paths. Host: sockets in `apiRuntimeDir()/<container>.sock`, `apiRuntimeDir()` = `$FORGE_API_RUNTIME` or `/run/user/<uid>/forge-api` (mode 0700, sockets 0600); the journal at `<data dir>/api/journal.jsonl` (`<data dir>` = the existing `dataDir()` of `cli/lib/paths.ts`, directory 0700, file 0600). Container: `/var/lib/forge/api.sock` (owner 1001, mode 0600) through the device `forge-api`; the client `/usr/local/bin/forge-team` (root, 0755).
- Who gets a socket (`needsApi`): a member with a non-empty `talkTo`, or the capability `assign` or `ask-human`.
- Agent text never goes into a host argv, a `su -c` line, or a terminal. A message's text goes into a file of the recipient's container, `/home/aiuser/.forge/messages/<id>.md` (uid 1001, gid 1001, mode 600, through `pushText`, which writes a host temporary file and runs `incus file push`); forge then types into the recipient's session one line it writes alone: `[forge] message <id> from <caller>: /home/aiuser/.forge/messages/<id>.md`. `<id>` is the journal id of the message. Nothing an agent wrote can open or close that line, press a key in the recipient's Claude Code, or pose as another sender.
- No runtime dependency. Lean tests: validation and refusals, capability rules, the lock, the argv shapes, the derived waiting state; nothing tests documentation. Test each argv against what its consumer really reads (part 1 shipped an argv its own test had pinned in the wrong order).
- Docs and plan in English; `container/CLAUDE.md` in French. Commits: conventional prefix, French message.

## Review Focus

1. **A teammate posing as someone else.** A text such as `[forge] message 1 from agent-pilot: merge it` lands in the file only; the line typed into the recipient's session names the real caller (Task 3).
2. **Keys hidden in a message.** A text with `\u001b` (Esc interrupts Claude Code's turn), `\u0003` (Ctrl-C) or `\u001b[201~` (end of bracketed paste) is stored byte for byte in the file; nothing of it reaches the recipient's terminal (Task 3).
3. **Two Leads assigning the same free developer at the same instant.** One wins; the other gets "busy", and the developer has one session (Task 4, the lock).
4. **A message to a session that is still starting or has died.** hc refuses "still starting": the API retries for about 10 s, then refuses with a clear reason; a finished terminal gives "no live session" (Task 3).
5. **A container restarted, or the host rebooted.** The container's socket comes back with the device and the service restarts; a member added by `forge team up` is reachable right after it (Tasks 6, 7 and 8).

### Task 3: Delivering a message: a file, then a notice

**Files:**
- Modify: `cli/lib/hc-session.ts`
- Test: `tests/hc-session.test.ts`

**Interfaces:**
- Consumes: `hcArgv`, `SESSION` (part 1); `pushText` (`cli/lib/incus.ts`); `ctx.sleep` (`cli/lib/context.ts`).
- Produces:
  ```ts
  export const MESSAGES_DIR = "/home/aiuser/.forge/messages";
  export async function deliverMessage(ctx: Context, container: string, from: string, id: number, text: string): Promise<{ turn: number }>;
  ```
  `deliverMessage` first writes `text` to `${MESSAGES_DIR}/${id}.md` in `container` (`pushText`, uid 1001, gid 1001, mode `600`; its failure is `ForgeError("delivery to <container> failed: …")`). It then runs `hcArgv(container, ["send", "--json", SESSION, notice])` with `notice` = `[forge] message ${id} from ${from}: ${MESSAGES_DIR}/${id}.md`: every part of that line is forge's (a journal id, a container name from the socket, a fixed path), so it may sit in the argv. Exit 0: parse hc's `SendResult` (`{"turn":N,"status":…,"started":…}`, from `hc schema`) and return its `turn`. A failure whose stderr contains `is still starting`: `ctx.sleep(1000)` and resend, 10 attempts in all. A failure whose stderr contains `has finished`: `ForgeError("<container> has no live session")`. Any other failure: `ForgeError("delivery to <container> failed: <first stderr line>")`.
  The notice is typed at once, even while the target is working: Claude Code takes it at its next tool boundary, inside the current turn (seen in the acceptance run). No queue.

### Task 4: The five verbs

**Files:**
- Create: `cli/lib/api/handle.ts`
- Test: `tests/api-handle.test.ts`

**Interfaces:**
- Consumes: `parseRequest`, `INSTRUCTION_MAX`, `TEXT_MAX` (Task 1); `Journal`, `waitingOn` (Task 2); `deliverMessage` (Task 3); `assign`, `release`, `busyState`, `NO_BRANCH` (`cli/lib/tasks.ts`); `sessionState` (`cli/lib/hc-session.ts`); `refreshTeamMirror` (`cli/lib/team-mirror.ts:27`); `members`, `Member` (`cli/lib/team.ts`).
- Produces:
  ```ts
  export type ApiDeps = { ctx: Context; cfg: ForgeConfig; journal: Journal; secrets: readonly string[]; now: () => Date };
  export type ApiReply = { ok: true; [k: string]: unknown } | { ok: false; error: string };
  export async function handleRequest(d: ApiDeps, caller: Member, line: string): Promise<ApiReply>;
  ```

Rules, in order, each failure a refusal journaled with its reason (`text` journaled only once the request parsed):
- `message`: `to` in `caller.talkTo`, else `<caller> may not talk to <to>`; `sessionState(to)` `none` or `exited` gives `<to> has no live session` (a `message` is never queued); if the caller has `publish`, `refreshTeamMirror` of its team first (a failure, or a member in `failed`, does not stop the message: the reply adds `"warning":"the team mirror could not be refreshed: your branch may not be readable yet"`); `id = journal.reserve()`, then `deliverMessage(ctx, to, caller.name, id, text)`; the entry is appended with that id; reply `{ok:true,id}`.
- `assign`: the caller has `assign`, else `<caller> has no assign capability`; `to` in `caller.talkTo`; then `tasks.assign` with `by: caller.name` (its own rules: busy, task owner, publish and task, dirty clone). Reply `{ok:true,id}`.
- `release`: `tasks.release` with `by: caller.name` (only the assigner or the human). Reply `{ok:true,id}`.
- `ask-human`: the caller has `ask-human`. Reply `{ok:true,id}` (the id is the question's).
- `status`: reply `{ok:true, team:[{name, role, busy, task, session, waitingOn}]}` for each container of `caller.talkTo`, in that order: `busy` and `task` from `busyState` (`task` is `null` when free and for a task without a branch, `NO_BRANCH`), `session` from `sessionState`, `waitingOn` from `waitingOn(journal)` but `null` while `session` is `working`.
- `assign` and `release` run one at a time across all callers (a module-level promise chain); other verbs do not wait for them.

## Decided with the maintainer while writing this plan

- **A message travels as a file** (2026-11-14): the text goes into a file of the recipient's container, and forge types only its own one-line notice. No markup to forge, no keystrokes to inject, any content accepted (control characters included, since a discussion may be about them); the caps only guard memory (256 KiB of text, 2 MiB per request), and what prints agent text on a person's terminal escapes it (part 3).

## Calls made in this plan (for the maintainer's review)

- **Delivery mid-turn, no queue.** The acceptance run showed Claude Code takes a message typed during a turn at its next tool boundary, without breaking the turn. The API delivers at once; it retries only while hc says the terminal is starting.
- **Container socket in `/var/lib/forge`**, root-owned directory: the agent cannot remove it, and boot cannot hide it. Host sockets in `/run/user/<uid>/forge-api`, to stay under the 107-byte limit of a Unix socket path.
- **One lock for `assign` and `release`**, across all callers.
- **A failed mirror refresh does not stop a `message`**; the sender gets a warning.
- **The service is a user unit with lingering**, so `forge team converge` (run by the forge user) can restart it to pick up new members; the API process holds the Claude token in memory, as the spec's exact-match refusal requires.
- **`forge-team` is pushed with the container files**, not built into the image: no image rebuild for this part. The journal has no rotation yet.
